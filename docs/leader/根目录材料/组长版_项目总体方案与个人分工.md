## 1 总体方案与任务书调整

项目面向校园食堂与商户，建设移动 H5 用户端和 Web 管理端。用户能浏览商品、维护购物车与地址、下单、模拟支付及跟踪订单；员工能维护分类、菜品和套餐，处理订单并查看营业统计与工作台。

用户端采用 Vue 3 + Vant H5，管理端采用 Vue 3 + Element Plus。后端采用 Java 17、Spring Boot 2.7.3、Spring MVC、MyBatis、MySQL 8；Redis、WebSocket 的适用范围和验证要求见技术方案。页面通过 REST/JSON 调用后端，正式源码在本项目 `code/backend/`。第三方登录与支付不作为课程演示的外部依赖。

原任务书已允许 H5 或小程序。由于缺少小程序账号、认证及发布条件，本项目选用已允许的 H5 路线，在浏览器演示完整业务。以下按用户本轮明确要求调整；这是组长方案，课程方是否需要重新提交任务书仍待按课程要求确认。

## 5 我的具体执行方法

我以需求 ID 建立追踪关系，先明确角色、权限和输入，再设计接口、事务、表字段及测试。所有业务金额由后端计算；当前用户身份来自 JWT；地址、购物车和订单必须按本人隔离；订单状态转换在 Service 层检查。外部服务使用课程替代方案，避免演示依赖私人账号与真实支付。

我先提交完整 OpenAPI 契约，再提供后端实现和测试数据。钱文博每批只需核对能否直接支撑页面调用，把问题定位到路径、字段、示例或异常；我更新契约与实现后再次交接。这是两人协作的具体接口，不要求队友替我开发后端，也不伪造对方的工作记录。

Git Flow 采用 `main`、`develop`、`feature/*`、必要的 `release/*` / `hotfix/*`；所有合并通过 PR，由另一人实际审阅。详细操作、PR 模板、交接表和阻塞处理见 [协作规范](docs/collaboration.md)。这些是执行规范；本次未据此自动初始化仓库、提交或推送，也没有真实远程 PR 链接。

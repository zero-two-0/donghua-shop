# 东华大学在线点餐系统个人分工与接口协作

## 一 我的职责

我是组员钱文博，主要负责用户端移动 H5 和商家管理端 Web 页面。用户端采用移动浏览器可访问的 H5 方案，不依赖微信小程序认证或发布；用户登录及在线支付按课程要求使用测试/模拟流程。我按双方确认的 OpenAPI 契约开发页面和请求调用，并参与需求、接口评审、联调、测试和会议记录。

本项目参考苍穹外卖，可复用已有页面素材、静态资源和交互思路，但需要逐项适配本项目的接口和课程范围。现有本地用户端 uni-app 工程带有 H5 配置，可以先验证 H5 编译；现有管理端模板依赖 Vue 2 + Element UI，与任务书 Vue 3 + Element Plus 的版本目标不同，因此先评估复用页面设计或迁移组件，再决定采用方式。上述为候选素材，只有构建和联调通过的部分才计入完成成果。

## 二 我负责的功能范围

| 前端模块 | 页面和交互 | 对接范围 |
| --- | --- | --- |
| 用户 H5 | 登录；分类与菜品列表、关键词查询；购物车数量调整和删除；提交订单及模拟支付结果；订单列表/详情/状态；收货地址维护；个人中心 | 用户登录、菜品查询、购物车、订单、地址 OpenAPI |
| 管理 Web | 员工登录；分类、菜品、套餐列表与表单；菜品起售/停售；订单接单、派送、完成；营业数据及工作台展示 | 员工登录、管理商品、订单和统计 OpenAPI |
| 前端公共能力 | API 请求封装、令牌保存与请求头、路由访问控制、统一错误提示、分页和表单校验、开发期 Mock 开关 | 按已冻结的通用响应和鉴权契约实现 |

页面数据只从本项目 API 或明确标记的开发 Mock 读取。Mock 用于前后端并行开发，提交或演示时清楚标识模式，并在接口联调阶段切换到真实后端。金额、订单状态和权限最终由服务端校验，前端显示不得取代服务端业务规则。

## 三 我负责的 OpenAPI 评审与前端接口清单

组长刘晟玺负责后端及 OpenAPI 初稿。我负责从前端实际调用出发逐条评审，并对“用户端字段、管理端表单/列表字段、分页、鉴权头、错误提示及加载状态”提供验收意见。以下路径是拟定接口清单，不代表已经冻结或已经实现；每组必须先在 `docs/api/openapi.yaml` 中评审确认，才开始该组正式联调。

统一约定建议为 JSON；所有业务响应采用团队确定的统一结构，分页返回当前页、页大小、总数及记录；受保护请求按契约传递 `Authorization: Bearer <token>`；错误响应提供稳定业务码和可展示消息。若复用素材接口与契约不一致，以本项目已评审的 OpenAPI 为准，适配层负责转换。

| 顺序 | 前端调用场景 | OpenAPI 拟定路径与方法 | 请求/响应评审重点 |
| --- | --- | --- | --- |
| 1 | 用户或员工登录 | `POST /api/user/auth/login`；`POST /api/admin/auth/login` | 登录身份字段、令牌、用户/员工概要、登录失败业务码；确定模拟账号策略 |
| 2 | 用户端分类和菜品 | `GET /api/categories`；`GET /api/dishes`；`GET /api/dishes/{dishId}` | 分类类型、关键词、分页、价格/图片/在售状态；明确空结果和停售处理 |
| 3 | 用户端购物车 | `GET /api/user/cart`；`POST /api/user/cart/items`；`PATCH /api/user/cart/items/{itemId}`；`DELETE /api/user/cart/items/{itemId}`；`DELETE /api/user/cart` | 商品/规格标识、数量边界、购物车小计；明确不存在、停售和数量不足响应 |
| 4 | 地址管理 | `GET /api/user/addresses`；`POST /api/user/addresses`；`PUT /api/user/addresses/{addressId}`；`DELETE /api/user/addresses/{addressId}` | 地址字段、默认地址规则、资源归属校验及删除失败情形 |
| 5 | 用户下单和模拟支付 | `POST /api/user/orders`；`POST /api/user/orders/{orderId}/mock-payment` | 地址、购物车校验、后端计算总额、订单号、初始状态、模拟支付后状态与重复提交处理 |
| 6 | 用户查单 | `GET /api/user/orders`；`GET /api/user/orders/{orderId}` | 分页、订单明细、状态枚举、只能访问当前用户订单 |
| 7 | 管理商品 | `GET/POST /api/admin/categories`；`PUT/DELETE /api/admin/categories/{categoryId}`；`GET/POST /api/admin/dishes`；`PUT/DELETE /api/admin/dishes/{dishId}`；`PATCH /api/admin/dishes/{dishId}/status`；套餐同样约定列表、新增、修改、删除与状态操作 | 筛选分页字段、必填校验、图片字段、起停售状态、删除受关联约束时的错误 |
| 8 | 管理订单及统计 | `GET /api/admin/orders`；`GET /api/admin/orders/{orderId}`；`PATCH /api/admin/orders/{orderId}/status`；`GET /api/admin/reports/overview` | 可执行状态迁移、筛选时间、状态按钮可用条件、汇总口径与空数据表现 |

路径只是建议的接口草案，最终命名、HTTP 状态码、统一响应外壳、金额精度、时间格式和字段名均以双方评审后的 `openapi.yaml` 为准。收到不兼容变更时，我会暂停该接口页面的联调，先通过 PR 更新契约并在会议纪要中记录原因和影响，再同步修改前端。

## 五 前端实现、测试和文档协作要求

- 契约评审前，我可以制作页面线框、组件和 Mock，但不将猜测字段写入生产请求代码。
- OpenAPI 中每项改动都通过 Git PR 审查。后端字段、枚举、路径或错误码变化时，同步更新接口文档、前端类型/调用和会议决策记录。
- 每完成一项前端功能，至少检查正常路径、无数据、接口失败、重复点击/表单校验和手机窄屏布局；将实际结果记入对应测试记录。
- 页面如使用现有素材，记录目录、复用范围、改动内容和实际构建/联调结果；截图或效果图作为说明，不替代测试记录。
- 会议纪要由参会者共同确认，记录当前只推进到哪一项、下一项输入、阻塞原因和责任人。

## 六 两人协作与 Git Flow

仓库按 `main`、`develop` 和 `feature/*` 分支协作。我的页面按功能开分支，提交 PR 到 `develop`；组长检查界面、契约一致性和实际运行情况后合并。组长的接口变更也由我检查其对页面与 OpenAPI 的影响。阶段验收后再将稳定版本发布到 `main`。每个 PR 关联任务和对应文档，附上验证步骤和结果；如果代码平台不支持分支保护，仍保留人工 PR 评审与合并记录。

日常共享资料统一纳入仓库 `docs/`：SRS、技术方案、ER/数据字典、`openapi.yaml`、会议纪要、测试与部署材料。我主要更新接口评审、前端兼容性和前端测试部分；总体范围和后端设计由组长负责，变更需要另一方 review。

## 七 阻塞项和处理办法

- 小程序认证或发布条件缺失：按任务书的 H5 选项交付，并用课程测试登录/模拟支付覆盖流程。
- uni-app H5 和管理端 Vue 2 模板的实际可构建性尚未通过本项目验证：第 2 周先做兼容性检查，再作素材采用决定。
- 前端依赖冻结契约进行联调：契约未确认时先用 Mock，并把缺失字段写成待评审问题；不因赶进度静默假设。
- 最终功能以可复现页面、真实接口调用、测试记录和 PR/文档记录为证，不将参考项目已有功能直接算作个人成果。

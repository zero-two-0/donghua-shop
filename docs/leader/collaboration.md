# 两人协作规范与可执行模板

编写人：刘晟玺。适用范围：本组 8 周工程项目管理过程。本文是可直接采用的工作规范，不代表远程仓库、PR、评审或会议已经建立/发生。当前实际证据不足的项目保持待执行。

## 1 协作的最小闭环

**我交设计/接口/后端 → 钱文博从前端调用角度核对 → 我根据具体问题修订 → 对方复核 → 形成真实阶段记录。** 不要求两个人同时写同一文件，也不把一个人的开发包装成双人已经共同完成。

每次协作只处理一批有明确输入输出的内容，周末验收一个主要交付包。第 3 周集中评审 A 认证/浏览、B 地址/购物车/订单、C 管理/统计；第 4/5 周分别开发后端/前端；第 6 周才以真实服务做整链路联调。

| 阶段 | 我给队友什么 | 队友应反馈什么 | 我下一步做什么 |
| --- | --- | --- | --- |
| 需求 | SRS、需求 ID、主流程、不做项 | 页面场景缺漏、不可实现/不清楚的需求 | 修订边界并保留问题与决定 |
| 技术与数据 | 架构、实体、字段、事务、配置说明 | 表单/展示/筛选字段是否具备 | 修订设计，说明数据来源 |
| 接口 A/B/C | 一批完整路径、Schema、成功/失败示例 | 路径+字段+具体调用场景的问题 | 修改 YAML 与实现，回传版本和检查结果 |
| 后端交接 | 源码、启动前置、测试身份、契约和真实自测 | 环境是否能按说明启动、响应是否可消费 | 补说明、修后端缺陷，不替对方写前端验收 |
| 联调与验收 | 可复现请求、日志摘要、后端修复 | 页面操作步骤、实际请求/响应与截图 | 定位归属，修复后按原步骤复测 |

## 2 RACI 责任矩阵

R=执行，A=最终整合负责，C=评审/提供输入，I=知会。此表描述职责，不宣称已经完成。

| 事项 | 刘晟玺 | 钱文博 |
| --- | --- | --- |
| 总体计划、范围和交付索引 | A/R | C |
| SRS、技术方案、数据库设计 | A/R | C |
| 全量 OpenAPI、全部后端与后端自测 | A/R | C |
| H5、管理 Web 与前端自测 | C | A/R |
| 后端 PR 审查 | R（作者及修订） | A/R（真实审阅） |
| 前端 PR 审查 | A/R（真实审阅） | R（作者及修订） |
| 后端缺陷与安全问题 | A/R | C |
| 前端缺陷与兼容问题 | C | A/R |
| 联调主流程、测试与部署包整合 | A/R | R（本人前端部分） |

数据库表/迁移、密钥、部署等受用户规则限制的操作即使有 RACI 也不自动授权。本文不允许擅自操作已有数据库、提交私人凭据或公开发布。

## 3 Git Flow 与 PR 合并

| 分支 | 用途 | 进入条件 |
| --- | --- | --- |
| `main` | 可验收的稳定版本 | 从 release / hotfix 通过 PR 合并并留验证记录 |
| `develop` | 阶段集成 | 功能 PR 审阅通过、相关验证完成 |
| `feature/<topic>` | 单个需求或同批相关接口/文档 | 从 develop 分出，描述需求 ID 与负责人 |
| `release/<version>` | 阶段收尾，修复/文档/验收 | 功能范围明确，禁止夹带未评审新功能 |
| `hotfix/<topic>` | 稳定版紧急修复 | 从 main 分出，修复后通过 PR 回 main 与 develop |

功能例名：`feature/srs-baseline`、`feature/user-order-api`、`feature/admin-dish`。这些是命名示例，不是当前已存在的分支。

执行顺序：负责人创建小范围任务→完成本批修改与自测→更新接口/文档→提交 PR→另一人实际审阅并提出意见→作者修订→审阅者复核→PR 合并。禁止作者自行填“对方已批准”。不要把未提交/未推送文件说成已经受远程版本控制；当前未初始化仓库时先保留本地材料，建立仓库/提交/推送按用户授权执行。

建议每个 PR 对应一个可审阅工作包，避免把需求、全部后端和所有页面一次堆入 PR。纯文档 PR 检查链接、事实和前后口径；后端 PR 检查契约、业务规则与真实验证；前端 PR 检查实际请求与界面行为。

### 可直接采用的 PR 描述

```markdown
## 目的
周次 / 需求 ID / 问题 ID：
触发场景与完成后的行为：

## 变更
- 实现或文档：
- 接口 / 字段 / 状态变化：
- 数据库设计影响（未授权不执行变更）：

## 验证
命令与运行环境：
实际结果 / 报告路径：
未验证范围及原因：

## 调用方影响
需要同步修改的页面或调用：
测试数据 / 示例：

## 审阅
需要另一人重点核对的项目：
真实意见与修订位置：
```

## 4 接口变更与前后端交接

OpenAPI 是共同契约。接口路径、方法、鉴权、字段、类型、枚举、分页或错误行为变化时，必须同时更新契约、实现和测试。不能仅发一句“接口改了”。具体接口不在聊天里重新定义一套，以文件和可追踪版本为准。

| 交接字段 | 必填内容 / 范例口径 |
| --- | --- |
| 交接批次 | A / B / C 或具体需求 ID |
| 生产者 / 接收者 | 刘晟玺 / 钱文博；反向反馈亦记录 |
| 基线 | 文件路径；有实际 commit/PR 时填真实标识 |
| 改动 | 路径、字段、旧/新行为、是否影响兼容 |
| 输入 | 运行前置、测试身份、必要样例数据；无真实凭据 |
| 验证 | 已实际执行的命令、结果及报告路径 |
| 未验证 | MySQL、Redis、浏览器等具体边界，不能只写“基本完成” |
| 问题 | 复现步骤、期望/实际、责任人和状态 |
| 接收结论 | 接收者真实填写；未确认就写“待确认” |

调用方问题推荐格式：`需求 FR-ORDER-03 → 具体路径 → 请求参数/身份 → 实际响应 → 期望行为 → 是否阻塞页面`。作者按此复现并给修复证据，避免没有定位依据的“接口不行”。

## 5 进度、阻塞与会议记录

每日结束前各自更新一次简短记录，不由组长代填队友完成量：

```text
日期 / 负责人：
今日完成（文件、需求或真实 PR）：
下一步（单个明确动作）：
阻塞（无则写无）：
需要对方提供什么、希望何时得到：
证据与未验证范围：
```

阻塞发生即暴露：标注影响周次、需求、负责人和最小解决动作；超过一个工作日仍未解决，在下一次同步优先处理并调整计划。涉及金额、越权或主流程不可用，立即标 P0 并停止相应验收；一般问题 P1 排入本周；体验增强 P2 不挤占关键路径。没有真实排期承诺时不替队友填具体时间。

| 阻塞字段 | 记录要求 |
| --- | --- |
| ID / 首次时间 | 真实登记，不回填假时间 |
| 影响与优先级 | 哪个接口/页面/里程碑无法继续 |
| 已尝试 | 命令、错误摘要或问题定位，不含私密配置 |
| 责任与依赖 | 谁处理、需要另一方/外部什么输入 |
| 下一检查点 | 一个可执行动作与可核对节点 |
| 关闭证据 | 原步骤复测通过的实际结果，不能仅凭口头“修了” |

会议记录使用 [启动记录模板](meetings/week1.md)，包含真实时间、参加人、材料版本、决定理由、未决项、行动项和证据。异步逐条评审也可以作为过程证据，但必须如实写“异步评审”，不能编成到场会议。

## 6 阶段完成标准与交付证据

1. 对应需求范围和文件齐全，链接可读，关键规则与契约一致。
2. 代码变更完成相关构建/测试，保留真实结果；无法运行写清依赖与未验证范围。
3. 另一人的实际意见已记录；“材料完成、待评审”可以报告，不能直接报告“双方验收通过”。
4. 高优先级缺陷有明确结论；未关闭项、范围变化和计划影响显式保留。
5. 有真实仓库时附 PR/commit；尚未建立远程时不编造提交、审阅、冻结或推送记录。

## 7 文档组织与证据边界

SRS 放 `week1/`，技术/数据放 `week2/`，契约/评审放 `week3/`，后端说明与真实测试放 `week4/`，会议与过程记录放 `meetings/`。需求、设计、契约、代码和测试通过需求 ID 互相追踪，成果入口是 [交付索引](README.md)。

本轮只写刘晟玺负责的材料与代码；组员旧文档及 H5/Python 演示不作为本人正式后端交付。后续本人可整合真实团队证据，但不得替组员宣称开发、自测、审阅已经完成。

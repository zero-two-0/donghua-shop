### 页面与接口对应范围

以下用于分工和查找，完整参数、方法及状态约束始终以 OpenAPI 为准。

| 页面 / 模块 | 对应接口区域 | 页面应体现 |
| --- | --- | --- |
| 用户登录、个人中心 | `POST /user/user/test-login` | 使用 `demo-user` 或 `demo-user-2`；保存当前测试身份和用户 token，提供地址/订单入口 |
| 商品首页 | `/user/category/list`、`/user/dish/list`、`/user/setmeal/list`、`/user/setmeal/dish/{id}`、`/user/shop/status` | 分类/查询、菜品口味、套餐组成、营业状态、加购 |
| 购物车 | `/user/shoppingCart/*` | 查询、加购、改数量、删除、清空；操作后重新读取服务端结果 |
| 地址 | `/user/addressBook/*` | 新增、编辑、删除、查询和默认地址选择 |
| 结算与支付 | `POST /user/order/submit`、`PUT /user/order/payment` | 使用本人地址，显示后端订单金额，模拟支付成功后再更新页面状态 |
| 用户订单 | `/user/order/historyOrders`、`/user/order/orderDetail/{id}`、`/user/order/cancel/{id}`、`/user/order/repetition/{id}`、`/user/order/reminder/{id}` | 列表、详情、状态、取消、再来一单与催单反馈；按允许状态展示操作 |
| 员工登录及管理 | `/admin/employee/*` | 账号登录、分页、新增/修改、启停、退出 |
| 分类/菜品/套餐 | `/admin/category/*`、`/admin/dish/*`、`/admin/setmeal/*` | 列表筛选、详情、增改删、起售/停售、口味和套餐组成 |
| 营业与订单管理 | `/admin/shop/*`、`/admin/order/*` | 营业切换、订单筛选/计数、详情、接单/拒单/取消/派送/完成 |
| 工作台与统计 | `/admin/workspace/businessData`、`/admin/order/statistics`、`/admin/report/turnoverStatistics` | 经营数据、订单状态计数、日期范围营业额；日/周展示使用契约数据，金额无真实营收含义 |

### 接入必须统一的规则

1. 新调用统一 `Authorization: Bearer <token>`；用户和员工 token 分别保存，不能混用。退出清除相应身份，401 引导相应端重新登录。
2. 响应格式是 `code/msg/data`，HTTP 200 仍可能 `code=0`；必须同时判断业务码。分页读取 `data.total` 和 `data.records`。
3. 金额由后端计算，前端展示用于交互；不自行认定付款或修改订单状态。支付页面明确标注“模拟支付”，不接微信 SDK。
4. 订单状态：1 待付款、2 待接单、3 已接单、4 派送中、5 已完成、6 已取消。支付状态：0 未付、1 已付、2 模拟退款。
5. 默认 `course` 环境没有已验收的 WebSocket 推送；先用查询/刷新完成状态跟踪。如设置轮询，离开页面时停止。
6. 默认课程环境不提供 OSS 上传接口；商品图片先使用复用静态素材或可访问图片路径。不要直接接入参考项目上传接口；需要上传功能时先登记契约变更。
7. 开发时使用 Vite 代理把 `/user`、`/admin` 请求转发到实际后端地址，并确认图片资源可访问。组员电脑的 `localhost:8080` 指向组员自己的服务；连接组长电脑时使用双方可达的地址。构建后的代理/部署配置在后续部署阶段验证。
8. 请求超时后先查询订单结果，避免自动重试下单造成重复订单。提交中禁用按钮；空数据、断网和业务失败都给出明确反馈。

## 3 第 6 周：两人共同联调

钱文博用浏览器操作、检查 Network 请求并记录；刘晟玺检查服务日志、数据与业务规则并修复后端。页面或请求封装问题由钱文博修复。接口确需调整时，刘晟玺同步 OpenAPI 与实现，钱文博更新调用，双方按原步骤复测。

先完成主流程与必要异常，不扩展无关测试或做大规模压测。

| 顺序 | 联调场景 | 通过标准 |
| --- | --- | --- |
| 1 | 两端登录 → 用户浏览真实商品 | 请求携带正确身份，数据来自实际 Java 服务 |
| 2 | 加购/改数量 → 新增或选择地址 → 下单 → 模拟支付 | 金额以服务端返回为准，订单生成后购物车清空，支付后变为待接单 |
| 3 | 员工查到同一订单 → 接单 → 派送 → 完成 → 用户刷新 | 用同一个订单 ID/订单号核对，双方看到状态 2→3→4→5 |
| 4 | 新建或修改商品 → 起售/停售 → 用户查询 | 管理修改能在用户侧体现；停售加购失败有提示 |
| 5 | 未登录/过期 token、空购物车、重复点击、非法订单状态 | 页面提示与实际响应一致，不显示虚假成功，不留下错误状态 |
| 6 | A 创建资源，B 使用 A 的地址/购物车/订单 ID 请求 | Java 服务拒绝越权，A 数据未被更改；隐藏按钮不能代替服务端校验 |
| 7 | 查询统计，核对刚完成的订单 | 日期范围与统计口径一致；记录真实数据差异并处理 |

场景 6 的请求级检查由刘晟玺负责，钱文博配合切换身份和记录页面行为。至少保留一次完整闭环的连续截图或短视频，再为关键异常保留简短记录即可。

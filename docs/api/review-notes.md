## 2 必须确认的问题（阻塞第 4 周后端开工）

### Q1 列表接口的联表字段：`categoryName`、`statusText`、`itemCount`

- **提出**：契约中 `Dish.categoryName`、`OrderSummary.statusText`、`OrderSummary.itemCount` 是必给字段，但数据库里都没有。
- **要求**：后端明确实现方式（JOIN / 二次查询 / 枚举转换 / 聚合），并在第 4 周自测记录里体现。
- **理由**：否则前端要么多发 N 次请求（性能差），要么自己翻译枚举（两端文案会漂移）。

### Q2 金额字段类型：字符串还是数字

- **提出**：契约声明 `price`/`amount` 为 `"18.00"` 字符串。
- **风险**：若后端用 `BigDecimal` 直接序列化，前端拿到的是数字 `18.0`，`toFixed` 与比较逻辑全部失效。
- **要求**：确认使用 `@JsonSerialize(using = ToStringSerializer.class)` 或 DTO 字段直接为 `String`。
- **临时兜底**：前端 `Number(x).toFixed(2)` 做了容错，但**不作为长期方案**。

### Q3 用户取消订单的接口缺失

- **提出**：契约中用户端只有下单与模拟支付，没有“取消订单”。管理端虽有 `1 → 6` 的迁移，但那是员工操作。
- **影响**：用户下单后未支付想放弃，只能等订单挂着。
- **建议**：二选一——① 第 4 周新增 `POST /user/orders/{orderId}/cancel`（仅允许 `status=1` 且本人）；② 明确“课程内不支持用户主动取消”，并在 SRS 第 2.4 节列入不做项。
- **我方倾向**：选 ②，控制范围；但需组长确认。

### Q4 令牌类型与越权语义

- **提出**：契约要求用户令牌调管理端接口返回 40301。
- **要求**：确认 JWT 载荷包含 `role`（user/admin）与 `id`，拦截器据此拒绝；不要只校验“有令牌”。

### Q5 开发期跨域方案

- **提出**：契约 `servers` 同时给了 `http://127.0.0.1:8080/api` 与 `/api`。
- **现状**：两个前端都用 Vite `server.proxy` 把 `/api` 转发到 8080，因此**不需要后端配置 CORS**。
- **要求**：确认保持代理方案；若后端要加 CORS，需允许 `http://127.0.0.1:5173` 与 `:5174`，并在文档中同步。

## 3 建议修改（不阻塞，但影响体验）

### S1 `dishFlavor` 的字符串格式需要固定

- 现在约定为 `辣度:微辣,加料:加面`（英文冒号与逗号）。前端按此拼接，后端按此存储。
- 建议：在契约里补 `pattern` 或示例；若后续要支持多选口味，应改为数组，届时属于破坏性变更。

### S2 模拟支付建议幂等

- 现在重复支付返回 40904。若用户双击“确认支付”，前端弹两个请求，第二个报错会让用户以为支付失败。
- 建议：后端对“已支付且状态为 2”的重复请求直接返回成功（幂等），或前端在请求期间禁用按钮（**前端已实现**）。

### S3 `GET /admin/reports/overview` 建议支持日期参数

- 现在只能看“今日/累计”。答辩若需展示某一周的营业额，需要重算。
- 建议：加可选 `beginDate`、`endDate`，缺省为今日；不实现也可，但需在 SRS 说明口径固定。

### S4 分页 `records` 的元素类型建议用泛型表达

- 现状用 `allOf + properties.records.items` 覆盖，语义正确但生成客户端时不友好。
- 建议：后端代码统一 `PageResult<T>`，契约可保留现状。

### S5 错误响应建议固定包含 `data`

- 成功响应有 `data`，错误响应示例里也有 `data: null`。请在实现中保证字段存在（值为 null），避免前端 `hasOwnProperty('code')` 分支之外的兼容代码。

### S6 `PATCH /admin/orders/{id}/status` 的 `status` 应限制为可迁移目标

- 契约 `enum: [3,4,5,6]`，但 `1 → 3` 也不合法。建议在 description 中给出完整迁移表（已写入），后端按表校验并返回 40909。
